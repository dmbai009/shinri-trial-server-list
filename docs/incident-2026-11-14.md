# Statistics outage: 14 November 2026

## Observed failure and evidence

At investigation time (approximately 09:58 UTC), the production statistics still contained the snapshot from **04:25:40 UTC** (06:25 Kyiv time). The `server-data` head was `e24d0f452d70cc79ac9156dcb47923341e968cd2`. Both the Raw GitHub branch URL and the JSON bundled into GitHub Pages contained that same old timestamp and data.

The Actions API returned **zero runs with `event=schedule`**. The five existing production runs were all successful `push` runs. The default branch was `main`, the workflow existed there and was `active`, the repository was public, non-archived, non-forked, and created earlier that day. Actions were enabled. This rules out a failed GameDig job, a disabled workflow, the 60-day inactivity rule, an incorrect default branch and a frontend-only cache freeze as the cause of the five-hour gap.

The failure was at the **scheduled-event dispatch stage**: GitHub never created scheduled runs. GitHub's public APIs do not expose why a particular scheduled event was not dispatched. We cannot honestly attribute the missing events to a specific internal GitHub defect or assert that the old valid cron range expression was invalid. GitHub documents schedule delays and dropped events; at investigation time its public status page did not report an Actions incident.

## Recovery test before changing the collector

Manual run [43583044362](https://github.com/dmbai009/shinri-trial-server-list/actions/runs/43583044362) used the original code. It restored the previous snapshot, queried all 50 servers successfully, and committed a new snapshot to `server-data` at **09:58:56 UTC**. Comparing normalized game data with the old snapshot found:

- **34 servers with changed population counts**;
- **35 servers with changed public player-name lists**.

Thus GameDig, normalization and snapshot writing were functional. Updating a timestamp alone was not considered sufficient evidence.

A second delivery detail was measured separately: the mutable Raw GitHub branch URL still returned the old response immediately after the commit, including with a new query string, while the immutable commit URL returned the new snapshot. The branch URL subsequently caught up. Observed headers were `Cache-Control: max-age=300` and `Access-Control-Allow-Origin: *`. Pages' old JSON had `max-age=600`. This is propagation/cache latency, not the cause of the five-hour absence of collections.

## Changes

- Replaced the combined scheduled build/deploy workflow with independent statistics and website workflows, each with its own concurrency group.
- Registered a new statistics workflow with explicit five-minute UTC minute entries and manual recovery. A range-expression syntax error is **not** claimed as the cause.
- Removed production dependence on a JSON snapshot bundled into Pages; the browser reads the public `server-data` source directly.
- Preserved query deadlines, independent failures, last successful data and explicit outdated player-list warnings.
- Added run provenance, collection gaps, content fingerprints and actual count/name-list change metrics to workflow summaries and the published snapshot.
- Added polling, cache regression, stale-data, rate-limit/backoff and content-change tests.

## Operational limits

GitHub's native scheduler is best effort. Re-registering a workflow and successful manual/push tests do not prove future scheduled dispatches. Verify actual `schedule` events in the workflow history. If there are no events, the problem is upstream of the collector; if runs fail, inspect the failing step; if branch data is fresh but the browser's data is older, compare the CDN payload and timestamp.

No independent paid or persistent scheduler is introduced. Consequently this project cannot promise a strict five-minute SLA or guarantee that GitHub will never miss another event. Visitors receive explicit stale-data warnings, and maintainers can inspect diagnostics and run collection manually without redeploying the website.
